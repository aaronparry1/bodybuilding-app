# Coordinated compatibility prescription semantics

D4E3C0 characterizes the current generated-slot prescription system without changing it. The system is cross-coupled: block branch, exercise role/family, lane, rep policy, set construction, starting load, drop-off and suitability jointly determine one coherent prescription branch.

The proposed aggregate semantic contract resolves that branch before arithmetic. Only the outer compatibility resolver may inspect legacy block state; future arithmetic consumes the aggregate, selected exercise facts, history, guidance and units. D4E2B calibration policy can later populate the same semantic domain, but equivalence is not assumed.

The characterized branch key is block type, exercise role/class and movement family, history state, loading capability/increment, guidance envelope, and session/slot context. Active branch fixtures cover hypertrophy primary compounds and accessories (fresh and established evidence), strength, power, and deload branches, with explicit unsupported outcomes for invalid role, class, loading, history, or contradictory guidance combinations. The matrix records rep range/final-set behavior, lane, set envelope, load hierarchy/rounding, drop-off/shutdown, suitability, and generated-slot outcome for each branch family.

The caller graph is: `generateWorkoutByFocus` → `selectExercisesFromTemplate` → `createGeneratedSlot` → rep/lane/set/load/drop-off/suitability helpers; planned-workout and extra-session consumers then receive the generated result. Direct helper exports are also used by compatibility tests. No current D4D2 caller enters this graph. Coupling is intentionally retained in the design: lane and role affect rep/set decisions, history and loading affect load, and lane/block affect drop-off and suitability. Therefore the aggregate must resolve atomically and must not fill independent defaults.

Proposed resolution outcomes are discriminated (`resolved`, unsupported branch/class/role/loading, invalid guidance/input, insufficient history, contradictory branch, or unsupported registry). The aggregate is immutable and contains policy identity/version, branch identity, all six semantic families, support classification, and reason codes, but no block object, block identity, workout, repository, or persistence callback. The sole compatibility resolver is the only future boundary allowed to project `TrainingBlock`/`BlockType`; downstream arithmetic receives only the aggregate and factual request inputs.

Extraction is staged: C2 contracts/registry, C3 aggregate resolver, C4 rep/lane migration, C5 drop-off/suitability, C6 set construction, C7 starting load, C8 one-slot seam, C9 generated-workout equivalence. Each phase keeps existing compatibility façades and has an independent rollback boundary. No-go conditions are missing fixtures, unrepresentable outputs, duplicated semantic calculation, bypassing exported callers, formula mismatch, or omitted mutable branch state. Current runtime remains deferred until compatibility and D4E2B fields have proven equivalent.

Completion requires every active branch and exported caller to be characterized, all downstream helpers to be block-free, one compatibility boundary to own projection, and generated-slot/workout outputs to remain exact. Current runtime wiring remains deferred.
