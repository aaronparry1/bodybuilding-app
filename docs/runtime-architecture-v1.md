# Runtime Architecture v1

Decision ID: 10G

Status: Locked architecture.

## Purpose

The Adaptive Strength Coach runtime must remain instant, offline-capable, deterministic, and scalable.

The app behaves like a game engine, not a CRUD application. Workout execution runs locally and deterministically; learning and cloud sync happen after the fact.

## Local First

Everything required to complete a workout must work offline.

Cloud services may enhance future coaching, backup, sync, or deep analysis. They must never block:

- starting a cached workout
- completing warm-ups
- logging sets
- receiving live safety/coaching decisions
- finishing the workout
- saving local evidence

## Coaching Event Bus

Coaching engines subscribe to events rather than calling one another directly.

Core events:

- workout_started
- warmup_completed
- set_completed
- rest_completed
- pain_reported
- exercise_completed
- workout_completed
- workout_abandoned
- session_review_completed

Selective engine wake-up is mandatory. A set completion should not recalculate the whole coaching system.

## Runtime Layers

### Layer 1: Real-Time

Runs during workouts. Strict latency requirements. No cloud dependency.

Examples:

- Live Workout Coaching
- Live Constraint Resolution
- Live Safety & Pain
- Productive Training Exposure

### Layer 2: Background

Runs after workouts or between sets. It must not block the workout UI.

Examples:

- Quality of Execution
- Post-Workout Review planning
- Coaching Evidence processing
- local sync queue preparation

### Layer 3: Deep Analysis

Runs asynchronously. May use cloud if available.

Examples:

- longer-horizon analysis
- heavy reporting
- cross-block review
- optional model refinement

## Latency Budgets

Each engine has a runtime budget. Anything exceeding its budget must move to background execution.

Real-time targets should remain in single-digit milliseconds wherever possible.

## Immutable Workout Principle

Generated workouts are immutable.

Only Live Workout Coaching may modify the active session state. Future sessions are rebuilt later using updated evidence.

## Evidence Queue

Workout execution never waits for learning.

Execution events and review feedback enter an evidence queue. Quality of Execution and Coaching Evidence process the queue asynchronously.

## Cached Knowledge

The following must be locally available before workout execution:

- Support Functions
- Exercise Knowledge Graph
- Method metadata
- Warm-up policies
- coaching metadata

## Explainability Cache

Reason codes generated by coaching engines should be reused when rendering explanations, summaries, and review screens. The app should not recalculate coaching explanations just to display them.

## Sync Strategy

Cloud services enhance coaching. They never become dependencies for workout execution.

Sync may update future coaching, future workout generation, and long-term analysis. It must not alter the active workout while the athlete is training.

## Regression Protections

Tests must prove:

- workout execution functions offline
- event bus prevents engine coupling
- real-time engines remain within latency budgets or move work to background
- learning never blocks the workout
- generated workouts remain immutable
- background sync updates future coaching only
